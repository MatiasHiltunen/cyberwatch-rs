# Architecture decision records

These decisions describe the example's design and known tradeoffs. They do not record student approval or a deployed environment. Revisit them against measured outcomes at P1/P2/P3.

| ADR | Alternatives considered | Decision and rationale | Consequence / revisit trigger |
|---|---|---|---|
| 001: Runtime and persistence | Embedded database in one replica; managed database with multiple API/worker instances | Keep embedded libSQL and one replica. A small course system benefits from bounded, understandable concurrency and a single recoverable dataset | No high availability; one replica only with current write coordination. Revisit if measured demand or recovery requirements justify distributed coordination |
| 002: Main deployment path | Azure Container Apps and managed storage; CSC Rahti/OpenShift with PVC; VM plus Compose | Supply portable Kubernetes/OpenShift configuration and a local Compose rehearsal. Select the alternative platform path for this example; operators validate CSC-specific constraints | Operator still owns namespaces, credentials, storage compatibility, ingress and TLS. Supporting files do not prove hosted deployment |
| 003: Assessment data | Live external feeds only; deterministic fixtures only; explicit selectable modes | Use explicit demo mode for repeatable tests and demonstrations; retain live ingestion for the real application | Synthetic content must remain visibly labelled; a demo health check cannot prove live source freshness |
| 004: Delivery identity | Long-lived broad cloud token; workload federation; no cloud credential in application release CI | Keep PR checks read-only and publication rights limited to explicit release jobs. Use an approved scoped operator identity for the actual target | A registry token or provenance statement cannot authorize arbitrary cluster deployment; host branch protection and deployment identities require configuration and denial evidence |
| 005: Supply-chain assurance | Floating release tags; immutable digest plus scans/provenance; absolute reproducible-build claim | Retain lockfile, scan dependencies/image, identify publication by digest, and preserve provenance when the release workflow runs | A digest identifies bytes, not their safety. Scans age; builder compromise remains possible. Strict reproducible builds are a separate future exercise |
| 006: Recovery | Copy an open database file; volume snapshot; database online backup API and validated restore | Use database-aware backup, integrity/hash checks and guarded restore; practice with disposable data before real recovery | Backup locality and operator privileges still matter. RTO/RPO are targets until exercised; incompatible schemas may prevent simple image rollback |
| 007: Security gate | Ignore all scanner findings; block every informational message; risk-based blocking with narrow exceptions | Fail actual configured blocking checks and require evidence for any proposed exception. No fabricated approvals or blanket scanner bypass | An exception needs owner, scope, expiry, compensating control and retest; it must not silently disable the gate |
| 008: Evidence traceability (revised 2026-09-22) | Shared evolving project and files; separate copies where technically useful | A shared repository, environment and files can serve YAMK282 and YAMK283 concurrently. Document course-specific claims and personal contributions against precise commits and runs | Separate copies are optional. The current Moodle course guide defines the actual assignments; this ADR does not add assessment requirements |
| 009: Production footprint | General-purpose image with operational tools; static scratch runtime; distroless glibc runtime with separate maintenance/development images | Use a pinned distroless production image and built-in readiness probe; keep Python recovery tools and development tooling in separate images. Optimize Rust size with full LTO and preserve panic unwinding for adapter isolation | Requires matching native runtime libraries and separate recovery tooling; longer optimized builds. Revisit against measured size, throughput, compatibility, and recovery results in the [production size guide](../production-size.md) |
| 010: Runtime distribution | Ship the entire source/course bundle; export a minimal runnable payload from the production image | Keep the source ZIP separate and allowlist the executable, dashboard assets, and license into a Linux runtime archive. Enforce architecture/content/size gates and attest production image, maintenance image, and archive separately | Native archives need compatible glibc/libgcc and the matching amd64/arm64 host. Evidence and size limits apply to the actual artifact; neither a small artifact nor an attestation proves safe behavior |

Use these records to understand design choices and their limits. The current Moodle course guide defines portfolio requirements; this repository does not maintain a second assignment list.
